# FDMA 读写并发能力验证与 `DMA4DDR_ctrl_v1` 架构审查

- 验证日期：2026-09-18
- 审查对象：`rtl/DMA4DDR_ctrl_v1.v`
- 外部依赖：本地授权的第三方 `uiFDMA.v`，不随本仓库分发
- 当前状态：**仅记录验证结论和设计限制，未修改 RTL**

## 1. 摘要

本次审查需要区分两个层级：

1. **`uiFDMA` AXI bridge 本体**：读、写方向具有独立控制状态，能够接受同拍到达的一个读请求和一个写请求，并让 AXI 写地址/写数据通道与读地址/读数据通道重叠工作。
2. **当前 `DMA4DDR_ctrl_v1` 顶层**：使用一个读写共用状态机和一条读写混合固定优先级链。顶层一次只向 `uiFDMA` 发出一个方向的请求，并等待该方向的完整 FDMA 事务结束后才重新仲裁，因此把 `uiFDMA` 原本具备的读写并发能力强制串行化。

因此，以下两个结论同时成立：

- 直接测试裸 `uiFDMA`：**支持一读一写同时启动、同时在途和数据阶段重叠**。
- 测试完整 `DMA4DDR_ctrl_v1 + uiFDMA`：**当前顶层不会同时发出读写请求，完整读写事务也不会重叠**。

这里的“并发”指 AXI 独立通道允许读写事务同时在途，不表示 DDR 颗粒在同一个物理存储周期真正同时读和写；后者仍由 MIG/DDR 控制器根据 DDR 时序进行交错调度。

## 3. 裸 `uiFDMA` 并发仿真

### 3.1 验证目标

确认在 `uiFDMA` 两个方向都空闲时，同一拍拉高：

```text
I_fdma_wareq = 1
I_fdma_rareq = 1
```

能否得到以下行为：

- `O_fdma_wbusy` 与 `O_fdma_rbusy` 同时有效；
- `M_AXI_AWVALID` 与 `M_AXI_ARVALID` 可以同时有效；
- AXI 写数据握手和读数据握手可以在相同周期发生；
- 两个方向能够独立完成并分别清除 busy。

### 3.2 仿真配置

```text
工具：Icarus Verilog 12.0 (devel)
时钟周期：10 ns
AXI 数据宽度：64 bit
写传输长度：8 beats
读传输长度：8 beats
M_AXI_B2B_SET：1
M_AXI_MAX_BURST_LEN：16
```

AXI slave 模型采用以下行为：

- 同拍给出读请求和写请求；
- 暂时拉低 `AWREADY`、`ARREADY`，直到观察到 `AWVALID`、`ARVALID` 同时存在，再同时接收两个地址；
- 写数据方向保持 `WREADY=1`；
- 读地址握手后连续返回 8 个读数据 beat；
- 用户侧读写 ready 均保持有效。

暂时施加地址背压不是功能要求，而是为了明确证明 AW 和 AR 两套控制不会互相抑制。解除背压后又观察到读写数据握手重叠，因此结论不只依赖地址 VALID 的暂存。

### 3.3 关键周期结果

```text
周期 C6 ：I_fdma_wareq=1，I_fdma_rareq=1
周期 C7 ：O_fdma_wbusy=1，O_fdma_rbusy=1
周期 C10：M_AXI_AWVALID=1，M_AXI_ARVALID=1
周期 C11～C17：AXI 写数据与读数据在相同周期完成握手
周期 C19：两个方向均完成，wbusy=0，rbusy=0
```

自动检查结果：

```text
busy_overlap       = 1
addr_valid_overlap = 1
data_overlap       = 1
final_wbusy        = 0
final_rbusy        = 0
PASS
```

### 3.4 结论

裸 `uiFDMA` 的读控制和写控制是独立的。它没有通过读 busy 阻止写启动，也没有通过写 busy 阻止读启动。只要 AXI 从设备能够分别接收 AW/W 和 AR/R 通道，一次读事务与一次写事务可以同时在途。

## 4. `DMA4DDR_ctrl_v1` 为什么不能并发

### 4.1 单一读写混合状态机

当前顶层只有一个共用状态机：

```text
IDLE
 ├─> WDDR_REQ -> WDDR -> DDR_WAIT ─┐
 └─> RDDR_REQ -> RDDR -> DDR_WAIT ─┘
                                     -> IDLE
```

`WDDR_REQ` 和 `RDDR_REQ` 是同一个状态寄存器的互斥取值，所以：

```text
O_fdma_wareq 与 O_fdma_rareq 不可能由该状态机同时发出。
```

### 4.2 读写混合固定优先级链

`IDLE` 中的当前选择顺序是：

```text
W0 -> R0 -> R1 -> W1 -> W2 -> W3 -> R2 -> R3 -> R4
```

实现形式是一条 `if / else if` 链。多个请求同拍存在时，只选择优先级最高的一个，其他请求不会在该拍被接受。

### 4.3 等待完整事务结束后才重新仲裁

顶层在请求被 `uiFDMA` 接受后进入 `DDR_WAIT`，退出条件为：

```text
I_fdma_wbusy == 0 && I_fdma_rbusy == 0
```

当前状态机每次本来只发出一个方向的请求，但仍等待两个 busy 都为空后才返回 `IDLE`。因此仲裁粒度是“完整 FDMA 传输”，而不是“请求接收”或“AXI burst 发射”。一个长写传输会阻止所有读请求，一个长读传输也会阻止所有写请求。

## 5. 当前架构的主要限制和风险

以下条目区分“已经由 RTL/仿真确认的限制”和“依赖系统负载才会显现的风险”。它们不一定都是立即造成错误的功能 bug，但会限制带宽利用率、实时性和后续扩展。

### 5.1 已确认：浪费 AXI 读写双向并发能力

`uiFDMA` 可以让一个读事务和一个写事务同时在途，但顶层只会启动一个方向。对于需要同时加载输入/权重并写回结果的 NPU，或者视频采集与显示并行的场景，这会阻止 load/store 重叠，增加端到端等待时间。

### 5.2 已确认：仲裁粒度过粗

重新仲裁发生在整个 FDMA 事务完成之后。传输越长，其他通道等待越久。即使 DDR/MIG 当前有能力接收另一方向的地址请求，顶层也不会利用它。

### 5.3 已确认：没有待处理读写命令队列

顶层没有独立的读命令 FIFO、写命令 FIFO 或 pending 位图。非获胜请求只能依赖源通道继续保持或重新产生 `REQ`，等待状态机下一次回到 `IDLE` 后重新检测。

当前仓库内置通道大多根据 FIFO 水位和通道状态产生电平型请求，因此请求条件通常会持续一段时间；但顶层接口没有显式的 `req_valid/req_ready` 接受契约。如果未来接入只脉冲一个周期的请求源，未获仲裁的请求可能没有被记录。

### 5.4 风险：固定优先级可能造成饥饿

持续有高优先级请求时，低优先级通道没有有限等待保证。例如 W0 持续满足条件时，位于优先级链后部的 R3/R4 可能长期得不到服务。DDR 带宽不足会增加排队，但固定优先级策略决定了等待是否公平；二者是不同问题。

### 5.5 已确认：读写方向被不必要地耦合

读模式选择和写模式选择已经分别存在，但启动控制仍由一个 `WR_S` 状态机管理。该结构使本来相互独立的 AW/W/B 与 AR/R 通道在控制层绑定在一起，也使后续增加通道、QoS、超时或性能计数器更复杂。

### 5.6 已确认：存在额外控制气泡

一次请求通常经历：

```text
IDLE -> xDDR_REQ -> xDDR -> DDR_WAIT -> IDLE
```

请求选择、REQ 拉高、等待 busy 应答和等待完整结束被分成多个阶段。相对长传输时固定开销不明显，但在大量短传输场景中会降低命令发射效率。

### 5.7 风险：时钟域关系依赖外部集成假设

顶层仲裁状态机运行在 `I_ui_clk`，而 `uiFDMA` 运行在 `M_AXI_ACLK`。`O_fdma_wareq/O_fdma_rareq` 与 `I_fdma_wbusy/I_fdma_rbusy` 之间没有显式 CDC 同步或异步握手。

如果系统保证 `I_ui_clk` 与 `M_AXI_ACLK` 是同一个时钟，该连接可以成立；但这一要求当前没有通过端口约束、RTL 断言或文档化接口契约强制表达。如果两个时钟不同，则存在亚稳态、脉冲遗漏和多位控制字段采样不一致的风险。

### 5.8 风险：缺少公平性和阻塞可观测性

当前没有公开以下诊断信息：

- 当前获准通道 ID；
- 每个通道等待周期；
- 饥饿/超时标志；
- 读写待处理命令数；
- AXI 读写重叠周期数；
- 各通道服务次数和传输 beat 数。

因此系统出现吞吐下降时，很难仅从顶层状态判断是 DDR 带宽不足、下游背压，还是固定优先级造成的长期等待。

## 6. 同拍请求的准确行为

当多个通道在同一拍请求时：

1. `IDLE` 的固定优先级链只选择第一个满足条件的通道；
2. 只有该通道对应方向的 FDMA 请求会被发出；
3. 其他请求不会被顶层锁存进队列；
4. 如果未获准通道继续保持请求条件，它会在后续重新参与仲裁；
5. 如果请求只存在一拍且源端没有自行保持，顶层没有机制保证该请求不丢失；
6. 持续高优先级流量可能让低优先级请求无限等待。

所以“同拍请求不会遗漏”只在源端能够保持/retry 请求这一隐含前提下成立，不能作为通用接口保证。

## 7. 对典型工作负载的影响

### 7.1 NPU/CNN

理想流水通常希望：

```text
读下一块输入/权重 + 计算当前块 + 写回上一块结果
```

当前 DMA 控制器至少会把 DDR 读和 DDR 写串行化，因此即使 NPU 内部做了双缓冲，也可能因为 DMA 端无法同时保持读写事务在途而出现装载或写回气泡。

### 7.2 视频系统

摄像头写 DDR 与显示控制器读 DDR 是典型的同时活跃场景。当前控制器可以在完整事务之间交替服务，但不能让一次视频写 FDMA 和一次视频读 FDMA 同时在 AXI 侧排队/执行。长 burst 与固定优先级组合还会增加低优先级视频/外设通道的最坏等待时间。

## 8. 后续建议方向（本次不实施）

在保持 `uiFDMA` 接口兼容的前提下，较合理的改造方向是：

```text
写通道请求 -> 写仲裁器 -> 写命令寄存器/FIFO -> uiFDMA 写接口
读通道请求 -> 读仲裁器 -> 读命令寄存器/FIFO -> uiFDMA 读接口
```

建议原则：

1. 将当前一个混合状态机拆为独立写控制器和独立读控制器；
2. 写方向最多保持一个 active command，读方向最多保持一个 active command，先利用 `uiFDMA` 已有的一读一写并发能力；
3. 每个方向至少增加一项 pending/skid 存储，明确 `valid/ready` 接受语义；
4. 读仲裁和写仲裁分别采用 round-robin、weighted round-robin 或带 aging 的优先级；
5. 地址、长度、模式和通道 ID 必须在命令接受时原子锁存；
6. 用通道 ID 路由读数据和写数据，而不是依赖可能被后续请求改写的组合选择；
7. 明确 `I_ui_clk == M_AXI_ACLK` 的集成要求，或者加入正规的 CDC 命令/完成握手；
8. 添加并发、背压、同拍竞争、长期公平性和短脉冲请求测试；
9. 增加服务次数、等待周期和读写重叠率计数器，区分 DDR 带宽瓶颈与仲裁瓶颈。

在进一步修改前，应先建立基线仿真：完整顶层同拍产生一个读请求和一个写请求，确认当前版本始终串行；改造后则要求两个方向可以分别被接受，并在 AXI slave 允许时出现 AW/W 与 AR/R 重叠。
